# 발표 Q&A 대비 — 가림게이트를 처음 보는 사람에게 설명하기 (11/12)

11/17 발표와 12/2 경진대회 질문에 대비한 정리다. 숫자는 모두 `docs/m3-numbers.md`와 `bench/results/`에서 왔다. 모르는 것은 "측정하지 않았다"고 말한다. 숫자를 지어내면 다음 질문에서 무너진다.

## 30초 설명

> 회사가 ChatGPT 같은 AI를 쓰면 고객 이름·전화번호가 그대로 외부 서버로 나갑니다. 가림게이트는 회사 PC에서 돌아가는 중간 관문입니다. 기존 서비스는 API 주소 한 줄만 바꾸면 됩니다. 이름·번호는 `[고객1]`, `[전화번호1]`처럼 가려서 보내고, 받은 답은 회사 PC 안에서 원래 값으로 되돌립니다. 그리고 요청이 쉬운지 어려운지 판단해서 쉬운 요청은 싼 모델이나 정해진 답으로 보냅니다. 무거운 로컬 LLM 없이 일반 사무용 PC의 CPU로 돕니다.

---

## 1. 핵심 개념 네 가지

### 1-1. 가명화와 복원 — "가려서 보내고, 돌아오면 되돌린다"

```
요청   김민수 고객(010-1234-5678)에게 배송 지연 사과 메일 써줘
나감   [고객1] 고객([전화번호1])에게 배송 지연 사과 메일 써줘     ← 외부 AI가 보는 글
답     [고객1] 고객님, 배송이 늦어져 죄송합니다 …
받음   김민수 고객님, 배송이 늦어져 죄송합니다 …                  ← 회사 PC에서 되돌림
```

- **누가 찾나**: 번호·이메일·주민번호·카드·계좌·주소는 정규식(코드)이 찾는다. 등록한 고객명·사내 고유명사는 사전이 찾는다. 사전에 없는 이름과 주소는 이름 인식 모델(14.7MB, CPU, 문장당 2ms)이 **위치**를 찾는다.
- **순서**: 주소 → 사전 → 이름 인식 모델의 이름 → 회사가 등록한 패턴 → 정규식 (D27). 주소를 먼저 가리는 이유가 있다. 사전 값이 주소 안에 들어 있으면 사전이 먼저 바꿔 버린다. 그러면 주소가 "마포구 [사내1]로 123"처럼 반쪽만 가려진다. 정규식과 모델이 찾은 주소 위치는 합쳐서 한 토큰으로 가린다.
- **대응표**(`[고객1]` → 김민수)는 그 요청을 처리하는 동안 **메모리에만** 있다. DB·로그·파일에 남기지 않는다(설계 결정 2번). 로그에는 가명화된 글만 남는다.
- **조사 교정**: 원래 값을 넣을 때 받침에 맞춰 조사를 고친다(`[고객1]은` → `김민수는`, `[고객2]가` → `박정훈이`).
- **복원 못 한 토큰**: AI가 요청에 없던 토큰을 지어내면 되돌릴 값이 없다. 사용자에게 그대로 보이고, 로그에 개수를 남긴다(답변 품질 측정 38건 중 1건, 한계).
- **AI가 토큰을 이해하나?** 가린 요청 앞에 지시를 붙인다(`config.yaml llm.placeholder_instruction`). 토큰은 대괄호까지 그대로 쓰고, 호칭은 "[고객1] 고객님"처럼 붙이고, 그 사람의 번호를 회사 문의처로 쓰지 말라는 내용이다. 마지막 두 가지는 답변 품질 측정에서 문제를 찾아 11/12에 더했다(#62).

### 1-2. 판단을 로컬과 클라우드로 나눈 이유 (D12)

기준은 하나다. **"판단하려면 원본을 봐야 하는가?"**

| 판단 | 어디서 | 이유 |
|---|---|---|
| 기밀인가 (엄격 수준에서 차단) | **로컬** 판단 모델 `gliclass:v4-edge` | 기밀은 가명화로 가려지지 않는다. 원문을 봐야 해서 밖으로 보낼 수 없다 |
| 원본 값이 필요한가, 위험·인젝션인가, 난이도, 의도 | **클라우드** OpenAI Decisions | `[고객1]`로 가려져 있어도 판단할 수 있다. 클라우드 모델이 훨씬 정확하다 |

- 순서가 중요하다. **가명화 → 로컬 판단 → (막히지 않았으면) 클라우드 판단 → LLM**. 클라우드에는 가명화된 글만 간다.
- 처음에는 판단을 전부 로컬 모델(`laya:multilingual`)로 하려 했다. 그런데 한국어 판단이 약했다(10/26, #5, D10). 그래서 판단 모델을 바꾸고 판단을 둘로 나눴다(10/27, D12). 판단까지 전부 로컬인 구성도 파인튜닝으로 시험했지만 기밀·위험 판단이 목표에 못 미쳤다(#22). 그래서 이 구성은 "완전 로컬" 옵션으로 남겼다.

### 1-3. 확률, 기준값, 신뢰도

- 판단 모델은 "예/아니오"가 아니라 **확률**을 준다(예: 기밀일 확률 0.12).
- **기준값**(threshold)은 코드에서 정한다. 확률이 기준값 이상이면 "예"다. 판단 모델은 계산·비교에 약해서 비교는 코드가 한다(설계 결정 6번).

| 판단 | 기준값 | 왜 이 값인가 |
|---|---|---|
| 기밀 (로컬) | **0.10** | 놓치는 쪽이 더 나쁘다. 낮게 잡아 재현율 92%(12/13)를 얻었다. 대신 오탐이 12%다. 그래서 기밀로 막는 것은 엄격 수준에서만 한다 |
| 원본 값 필요 (클라우드) | 0.02 | 원본이 필요한 요청을 놓치면 AI가 엉뚱한 값을 지어낸다. 18/18을 막았고 잘못 막은 것은 0.6%다 |
| 위험 (클라우드) | 0.5 | 13/13을 막았고 잘못 막은 것은 0% |
| 복잡 (클라우드) | 0.08 | 이 값 이상이면 고성능 모델 |

- 기준값은 라벨을 검토한 테스트셋(#6)으로 정했다. 새 모델의 기준값을 테스트셋으로 다시 맞추지는 않는다. 그렇게 하면 시험 문제로 공부한 셈이 된다.
- **신뢰도는 화면에서 "확률 0.12 / 기준 0.10"으로 보여 준다(D24).** 보통 쓰는 신뢰도 공식 |2p − 1|은 0.5에서 얼마나 떨어졌는지를 잰다. 기준값이 0.10이면 기준 바로 위(0.12)인데도 신뢰도가 0.76으로 나온다. 실제로 로컬 기밀 판단에서 신뢰도 0.8 미만 구간의 정확도는 36%(12/33)였다.
- 신뢰도가 낮으면 고성능으로 보내는 기준값(`min_confidence`)은 두지 않았다. 값을 올려도 정확도는 좋아지지 않고 비용만 늘었다(D24).

### 1-4. 라우팅 — 어느 길로 보낼까

```
가명화 → ① FAQ? ──예──→ 템플릿 답 (아무것도 밖으로 나가지 않음, 비용 0)
          │아니오
          ↓
        ② 로컬 판단 ──엄격 + 기밀──→ 차단
          ↓
        ③ 클라우드 판단 ──위험·원본 필요·무관──→ 차단 + 안내문
          ↓                  └──복잡──→ 고성능 모델
          └────────────단순────→ 저렴한 모델
```

- 경로를 고르는 것은 **코드**다. 같은 판단 결과면 언제나 같은 경로가 나와야 해서 모델에 맡기지 않는다.
- 애매하면 고성능으로 보낸다. 정상 요청을 막는 것보다 비싼 모델로 보내는 편이 낫다.
- 차단 안내문은 LLM이 만들지 않고 고정 문구를 쓴다. 위험한 요청을 안내문 때문에 LLM에 보내지 않기 위해서다.
- 판단이 실패하면 기본 수준은 저렴한 모델로, 엄격 수준은 차단한다. 공격자가 판단을 일부러 실패시켜 우회하지 못하게 하려는 것이다(#12 보안 검토).

### 기술 선택

| 질문 | 답 |
|---|---|
| 왜 로컬 LLM을 안 쓰나요? | 가벼움이 핵심이다. 로컬 LLM은 GPU나 큰 메모리가 필요하다. 판단 모델(2.2GB)과 이름 인식 모델(14.7MB)은 일반 PC의 CPU로 돈다. 로컬 LLM은 "완전 로컬" 옵션으로만 둔다(설계 결정 3번) |
| 그냥 LLM한테 "개인정보 가려줘"라고 하면 안 되나요? | 그러려면 원문을 LLM에 보내야 한다. 그리고 생성 모델은 위치를 정확히 짚거나 같은 입력에 늘 같은 결과를 내는 일에 약하다. 가리는 일은 코드와 작은 모델이, 글을 쓰는 일은 LLM이 한다(설계 결정 1번) |
| 왜 Spring Boot에서 Python으로 바꿨나요? | 판단 모델 SDK와 ML 도구가 Python 중심이다. AI와 함께 만드는 효율도 높았다 (decisions.md) |
| 기존 서비스는 뭘 바꿔야 하나요? | API 주소 한 줄이다. OpenAI와 같은 형식(`/v1/chat/completions`)을 받는다 |
| 업종이 바뀌면요? | 업종 프리셋 한 줄로 FAQ·사전·이름이 아닌 낱말 목록이 바뀐다. 테스트셋도 쇼핑몰·의료·금융·공공 4개 업종으로 검증했다 (D13, D22) |

### 한계 (먼저 말하는 편이 낫다 — `docs/limitations.md`)

| 질문 | 답 |
|---|---|
| 막히는 요청이 많지 않나요? | 맞다. 개인정보가 든 요청의 약 3분의 1은 원본 값이 필요해서 막힌다(주민번호로 나이 계산 등). 이것은 버그가 아니라 정책이다. 원본을 보내지 않겠다는 약속을 지키면 그런 요청은 처리할 수 없다. 완전 로컬 모드가 이 문제의 답이고 다음 단계다 |
| 그럼 왜 써야 하나요? | 메일·요약·안내문처럼 이름이 들어가도 이름의 실제 값이 필요 없는 일이 업무의 대부분이다. 이런 일은 가려서 보내도 답의 내용이 같다. 자연스러움만 조금 떨어진다 (#62) |
| 처음 목표인 토큰 절약은요? | 단순 요청에서는 확실히 준다. 전체 절감은 요청 구성에 달렸다. 보안 기능을 넣으면서 판단 한 번이 더 들었지만, 판단 비용은 전체의 1% 남짓이다 |
| 사용자 평가는요? | 발표 뒤(11/18~12/1) 웹 체험판으로 10명 이상에게 받는다. 결과는 12/8에 제출한다 |

## 3. 답하기 어려운 질문이 오면

- **측정하지 않은 것**: "측정하지 않았습니다. 지금 근거는 ○○입니다"라고 말한다. 예: 실제 회사 데이터 성능, 동시 사용자 처리량, 영어 요청.
- **"다른 제품과 비교하면?"**: 비교 측정은 하지 않았다. 차이는 설치 방식이다. 클라우드 보안 게이트웨이와 달리 원문이 회사 PC를 떠나지 않고, 로컬 LLM 방식과 달리 GPU가 필요 없다.
- **"기준값을 테스트셋으로 정했으면 수치가 부풀려진 것 아닌가?"**: 맞는 지적이다. 판단 기준값은 라벨을 검토한 테스트셋으로 골랐다. 그래서 판단 정확도는 실제보다 좋게 나왔을 수 있다. 대신 세 가지를 지켰다. 가명화 99.5%는 테스트셋이 아니라 따로 만든 데이터 622개로 쟀다. 이미 정한 기준값을 새 모델에 맞춰 다시 고치지 않았다(D24). 답변 품질을 고친 뒤 확인은 테스트셋 밖 문장으로 했다. 웹 체험판의 실제 요청이 다음 검증이다.
- **"정말 실서비스에 쓸 수 있나?"**: 1인 수업 프로젝트다. 회원 관리·멀티 테넌트·운영 모니터링은 범위 밖이다. 설치형으로 한 PC에서 한 회사가 쓰는 것까지가 목표다.
