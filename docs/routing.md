# 라우팅 정책 (`gateway/routing/`, #10)

판단 결과와 보안 수준으로 요청을 어디로 보낼지 정한다: **템플릿 / 저렴한 모델 / 고성능 모델 / 차단**.

**생성형 AI의 역할**
- 판단 모델(로컬 소형 모델, 클라우드 Decisions)이 요청을 분류한다.
- 라우팅은 그 분류를 규칙으로 경로에 연결하는 **코드**다. 같은 판단 결과면 언제나 같은 경로가 나와야 하므로 모델에 맡기지 않는다.

## 경로를 정하는 세 곳 (D12의 처리 순서)

```
가명화 → ① match_faq → 로컬 판단 → ② decide_after_local → 클라우드 판단 → ③ decide_after_cloud
            템플릿          엄격: 기밀·남은 개인정보 → 차단          차단 / 고성능 / 저렴
```

| 함수 | 언제 | 하는 일 |
|---|---|---|
| `match_faq(text, faq)` | 판단 전 | 등록된 FAQ면 템플릿 답변. 판단 API도 LLM도 부르지 않아 **밖으로 아무것도 나가지 않는다** |
| `decide_after_local(local, level, messages)` | 로컬 판단 뒤 | 엄격 수준에서만 차단. 차단하지 않으면 `None` → 클라우드 판단으로 |
| `decide_after_cloud(cloud, cfg)` | 클라우드 판단 뒤 | 차단 / 고성능 / 저렴 |

결과는 `Decision(route, reasons, message, faq_id)`이다.
- `reasons`: 경로를 고른 이유 코드. 차단이면 걸린 사유 **전부**가 들어간다.
- `message`: 차단 안내문 또는 템플릿 답변. LLM을 부르는 경로에서는 `None`이다.

## 규칙

### ① FAQ (코드)
- FAQ마다 단어 묶음을 등록한다. 한 묶음의 단어가 모두 들어 있으면 그 FAQ로 본다. 띄어쓰기는 무시한다.
- **잘못 맞히는 쪽이 놓치는 쪽보다 나쁘다.** 업무 요청에 엉뚱한 정해진 답이 나가기 때문이다. 그래서 다음 문장은 FAQ로 보지 않는다.
  - `max_chars`(40자)보다 긴 문장
  - "써 줘·작성·정리해·짜 줘" 같은 업무 요청 표현이 있는 문장
- 놓친 FAQ는 클라우드 판단에서 의도가 `faq`로 나오고, 저렴한 모델이 답한다(`faq_unregistered`).

### ② 로컬 판단 뒤
| 보안 수준 | 동작 |
|---|---|
| 기본 | 막지 않는다. 남은 개인정보 의심을 어떻게 처리할지는 M2 가명화 뒤에 정한다 |
| 엄격 | 기밀 → 차단(`confidential`), 남은 개인정보 의심 → 차단(`pii_residual`). **로컬 판단 실패 → 차단**(`local_error`). 기밀인지 확인할 수 없으면 막는다 |
| 완전 로컬 | 로컬 LLM 경로는 11/18 이후 선택 기능이다. 그 전까지 엄격 수준처럼 동작한다 |

### ③ 클라우드 판단 뒤 (순서대로)
1. 판단 실패 → `on_error_route` (저렴)
2. 차단 사유를 모두 모은다: 위험(`risky`), 원본 필요(`needs_raw`), 위험·원본 필요 판단 거부(`refused`, D16), 무관(`off_topic`). 하나라도 있으면 차단한다.
3. 난이도·의도 판단 거부 → `on_routing_refusal` (고성능, D16)
4. 난이도·의도 신뢰도가 `min_confidence` 미만 → `low_confidence_route` (고성능). 지금은 기준값이 비어 있어 꺼져 있다.
5. 복잡 → 고성능, 나머지 → 저렴

- **애매한 "무관"은 막지 않는다.** 신뢰도가 기준에 못 미치는 무관 판단은 차단 대신 4번(고성능)으로 간다. 정상 요청을 막는 것보다 비싼 모델로 보내는 편이 낫다("애매하면 고성능").

## 차단 사유가 여러 개일 때 (10/31 결정)
- 사용자에게는 **우선순위가 가장 높은 사유의 안내문 하나**를 보낸다. `reasons`에는 모든 사유를 남겨 로그와 관리 화면에 표시한다.
- 우선순위(`BLOCK_PRIORITY`): **위험 → 원본 필요 → 판단 거부 → 무관** → (로컬) 기밀 → 남은 개인정보 → (오류) 로컬 실패 → 클라우드 실패 → 신뢰도 미달
- 이유: 인젝션 시도는 대개 업무와도 무관하다.
  - 시도한 사람에게는 "업무와 무관합니다"보다 "보안 정책상 처리할 수 없습니다"가 정확한 안내다.
  - 관리자에게는 두 사유가 다 보여야 판단 근거가 남는다.
- 안내문은 `config.yaml`의 `routing.block_messages`에 사유별로 둔다. 위험한 요청을 안내문 생성 때문에 LLM에 보내지 않으려고 고정 문구를 쓴다.

## 설정 (`config.yaml`)
| 키 | 내용 |
|---|---|
| `faq.entries` | FAQ id, 단어 묶음, 정해 둔 답. **업종별 설정**(D13)이라 회사가 바꾼다. 지금은 시연용 쇼핑몰 FAQ 5개 |
| `faq.max_chars`, `faq.exclude_words` | FAQ로 보지 않을 문장의 조건 |
| `routing.block_messages` | 차단 사유별 안내문 |
| `decision.cloud.on_refusal`, `on_routing_refusal`, `on_error_route` | 판단 거부·실패 때의 경로 (D16) |
| `routing.min_confidence`, `low_confidence_route` | 신뢰도 기준 (M3에서 정한다) |

## FAQ 매칭 확인 (10/31)
| 문장 | FAQ로 잡힘 | 잘못 잡힘 |
|---|---|---|
| 테스트셋 T 템플릿 15행 | 15/15 | — |
| 테스트셋 템플릿이 아닌 160행 | — | 0 (처음 1건 → 고침, 아래) |
| **처음 보는 문장**: 생성 시험 단순 FAQ 30문장 | 16/30 | — |
| **처음 보는 문장**: 생성 시험 다른 조건 210문장 | — | 0 |

- 처음 잡힌 오탐 1건: "신입 CS 상담원 교육 커리큘럼을 4주 과정으로 짜 줘"(T042)가 상담 시간 FAQ에 걸렸다. "짜 줘"를 업무 요청 표현에 넣고 `[상담원]` 단독 조건을 `[상담원, 연결]`·`[상담원, 통화]`로 좁혔다. 테스트에도 넣었다.
- 테스트셋 15/15는 단어 묶음을 그 문장들을 보면서 만든 결과라 낙관적인 수치다. **처음 보는 문장(생성 시험)의 16/30이 실제에 가깝다.**
  - 놓친 14개 중 8개는 등록하지 않은 주제다(포인트, 쿠폰, AS, 배송비 등).
  - 등록한 주제에서 놓친 6개는 동의어다("발송되나요", "영업시간").
  - 이 숫자를 보고 단어를 더 넣으면 처음 보는 문장이 아니게 되므로 그대로 두었다.
- 코드 매칭은 **정밀도를 지키는 대신 재현율을 포기**한다. 놓친 FAQ는 저렴한 모델이 답하므로 손해가 작다.
  - FAQ를 더 많이 잡으려면 회사가 동의어를 등록하면 된다.
  - 다른 방법은 로컬 판단 모델에 "어느 FAQ인가" 선택 질문을 하나 더 하는 것이다. 이는 설계 변경이라 M3 이후에 검토한다.
