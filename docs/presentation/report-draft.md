## 생성형 AI 활용 목적 및 개요 (3개 이상)
1. 개발 도구: 1인·짧은 일정(10/11~11/17) 안에 게이트웨이·관리 화면·설치 스크립트·측정 도구를 만들기 위해 Claude Code에 코드·시험 작성과 분석을 맡겼다. 이슈마다 "AI가 계획 제안 → 내가 확인·수정 → 구현·시험 → 내가 리뷰·머지" 순서로 진행했다.
2. 제품 속 판단: 로컬 판단 모델(gliclass, CPU)이 원문의 기밀 여부를, 클라우드 판단 API(OpenAI Decisions)가 가명화된 문장으로 원본 값 필요·위험·난이도를 판단해 정해 둔 답·저렴한 모델·고성능 모델·차단 중 경로를 고른다.
3. 제품 속 생성·인식: LLM이 가명 토큰([고객1])이 든 요청으로 답변을 쓰고, 이름 인식 모델이 사전에 없는 이름·주소의 위치를 찾는다. 바꾸기·되돌리기·계산은 코드가 한다.
4. 기록·발표: 설계 결정 기록, AI 활용 기록, 측정 결과 정리, 발표 자료와 시연 대본 초안 작성에 활용했다.

## 생성형 AI 활용 성과 (4개 이상)
1. 일정보다 먼저 완성: 커밋한 날 18일, PR 46개, 이슈 42개, 자동 시험 505개를 갖춘 게이트웨이·관리 화면·설치 스크립트를 만들었고, 측정 단계(M3)를 계획보다 이틀 먼저 끝냈다.
2. 측정으로 확인한 결과: 개인정보 가명화 99.5%(619/622), 실제 값이 필요한 요청 차단 100%(18/18), 경로 정확도 89%(쇼핑몰 97%), 쉬운 요청 비용 95~100% 절감. AI가 만든 측정 실행기로 테스트셋 190행(가상 데이터)을 돌렸다.
3. 보안 품질: 커밋마다 AI 보안 검토를 받아 관리 기능 인증, 비밀번호 잠금 우회, 주소 가명화 빈틈 같은 문제를 찾아 고쳤다. 실제 사고는 원래 값 없이 기록하고 같은 모양의 시험을 더했다.
4. 새 도구를 빠르게 도입: 2026년 9월 이후 나온 도구(Ollaya, OpenAI Decisions, Cloudflare Tunnel)는 AI에게 공식 문서를 먼저 확인시킨 뒤 적용했다. 판단 모델 여러 개를 같은 테스트셋으로 비교해 최종 구성을 정했다.
5. 기록이 남았다: 설계 결정 28건과 AI 활용 기록 52줄이 발표·면담의 근거가 되었다.

## 생성형 AI 사용 후 느낀점 (2개 이상)
1. "무엇을 AI에게 맡기고 무엇을 내가 정할지" 나누는 것이 핵심이었다. 코드·시험·측정은 빠르게 맡길 수 있었지만, 원문이 필요한 판단만 로컬에서 하는 구조, 무엇을 막을지의 정책, 화면 설계는 직접 써 보고 정해야 했다. 화면은 세 번 고쳤다.
2. AI가 만든 결과도 확인해야 했다. 시험이 통과해도 실제 모델·실제 화면에서는 다르게 동작한 경우(주소 가명화 빈틈, 발표 자료의 한글 줄바꿈 등)가 있어, 측정과 직접 사용으로 찾아 고쳤다.
3. 직접 써 보며 한계도 보였다. 개인정보가 든 요청의 1/3은 실제 값이 필요해 막힌다. 범위는 지키되 한계와 다음 단계(PC 안에서 처리하는 완전 로컬 모드)로 정리했다.
