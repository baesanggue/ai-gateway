# 파일 검사 (`gateway/files/`, #50)

PDF·워드·엑셀 속 개인정보를 찾아 안내하고, AI에 붙여넣어도 되는 **가명화된 텍스트**를 만든다. 11/03 면담 의견을 반영했다: 파일 속 개인정보를 판단해 안내문을 띄우는 기능이 있으면 좋다.

**생성형 AI의 역할**: 이름 인식 모델(로컬, CPU)이 사전에 없는 이름과 정규식이 못 가린 주소의 위치를 찾는다(D23). 글자 뽑기와 가명화(바꾸기)는 코드가 한다(설계 결정 1번). 판단 모델은 쓰지 않는다. 긴 문서가 판단 모델이 읽을 수 있는 길이를 넘기 때문이다(D19, #39). 이름 인식 모델은 긴 글도 구간으로 나눠 끝까지 읽는다. 파일은 이 PC 밖으로 나가지 않는다.

## 사용
```bash
uv run python -m gateway.files 고객명단.xlsx --masked-out 가명화.txt
```
```
개인정보 4개를 찾았습니다: 고객 2개, 전화번호 1개, 회원번호 1개. 위치: '고객' 시트 A2, '고객' 시트 B2, …
이 파일을 그대로 외부 AI에 올리지 말고, 가명화된 텍스트를 쓰세요.
```
- API: `POST /v1/files/scan` `{"filename": "고객명단.xlsx", "content_base64": "…"}`
  - 응답: `has_pii`, `summary`, `counts`, `findings`(위치별 종류·개수), `unmasked`, `suspected`(이름 인식 모델이 봤지만 가리지 못한 종류: 시·도 없이 쓴 주소 등), `masked_text`
  - 게이트웨이 키 규칙은 채팅과 같다(D20).
- 시연 화면의 파일 끌어다 놓기는 M4에서 이 API를 부른다.

## 무엇을 읽나
| 형식 | 읽는 곳 | 위치 표시 |
|---|---|---|
| PDF | 글자 층 | `3쪽` |
| DOCX | 문단, 표, 머리글·바닥글 | `2번째 문단`, `표 1 1행`, `머리글(구역 1)` |
| XLSX | 셀 값(수식은 계산된 값) | `'고객' 시트 B2` |
| TXT·CSV | 줄 (UTF-8, 한국어 엑셀의 CP949 CSV) | `2번째 줄` |

- 검사 규칙은 채팅과 같다: 사용자 사전 → 이름 인식 모델(사전에 없는 이름 → `[이름1]`) → 회사별 식별번호(업종 프리셋) → 정규식 → 마지막 검사.
- 이름 인식 모델은 파일 전체를 이어 한 번에 읽힌다(칸마다 부르지 않는다).
- 파일 전체를 한 번에 가명화해서, 같은 값은 어느 칸에 있든 같은 토큰이 된다.
- **결과에는 값을 넣지 않는다.** 종류, 개수, 위치, 가명화된 텍스트만 준다. 복원 대응표도 돌려주지 않는다. 원본은 사용자 파일에 있다.

## 읽지 못하는 파일
| 경우 | 안내 (`code`) |
|---|---|
| 스캔 PDF·이미지만 든 파일 | 글자를 읽을 수 없음 (`no_text`). OCR은 범위 밖이다 |
| 암호 PDF | `encrypted` |
| 지원하지 않는 형식(hwp 등), 이름만 바꾼 파일 | `unsupported`, `unreadable` |

## 안전장치
- 크기 상한 10MB. 파일 앞부분(`%PDF`, `PK`)으로 형식을 확인하고 깊이 읽는다.
- docx·xlsx는 zip이다. **압축 폭탄**을 막으려고 풀린 크기 합(100MB), 압축률(100배), 항목 수를 파싱 전에 본다.
- XML 외부 엔티티를 풀지 않는다. python-docx는 `resolve_entities=False`, openpyxl은 defusedxml을 쓴다(없으면 엑셀을 읽지 않는다).
- PDF 안의 압축된 데이터도 하나를 풀었을 때 20MB까지만 푼다(pypdf 설정, 검사 함수 안에서만 적용). 넘으면 `zip_bomb`.
- 쪽(500)·셀(20만)·글자(200만)·PDF 시간(30초) 상한은 **읽는 도중에** 확인한다. 다 읽은 뒤에 세면 그 전에 시간·메모리가 먼저 든다.
  - docx·xlsx 안 XML은 파서보다 먼저, 트리를 만들지 않고 훑어서 요소 수(150만)·셀 수·한 행의 칸 수(XFD열 16,384)를 센다. 엑셀 파서는 한 행을 통째로 메모리에 올린 뒤 넘겨 주기 때문이다. 이때 엔티티 선언이 있거나 훑지 못한 XML이 있으면 읽지 않는다(`unreadable`).
    - 훑는 대상: 이름이 `.xml`·`.rels`인 부분, `[Content_Types].xml`에 XML로 적힌 부분, 앞부분이 XML처럼 보이는 부분(BOM 없는 UTF-16·32, EBCDIC 포함, 앞 공백은 길이와 상관없이 건너뛰고 봄). 확장자는 OPC 방식(마지막 `.` 뒤, 없으면 빈 값)으로 본다. 파서는 읽는데 검사는 건너뛰는 부분이 없게 넓게 잡는다. 이미지·글꼴·인쇄 설정 같은 이진 부분만 건너뛴다.
  - 엑셀은 값이 없는 칸과 빈 행도 센다. 파일에 적힌 시트 크기(`A1:XFD1048576` 같은 값)는 믿지 않고 실제로 있는 칸만 돈다.
  - PDF는 pypdf가 연산자마다 부르는 함수로 **한 쪽 안에서도** 시간·글자를 본다. 양식 객체(XObject)를 수백 번 불러 쓰는 쪽도 중간에 멈춘다. pypdf가 양식 안에서 난 예외를 삼키지만, 바깥 쪽의 다음 연산자에서 다시 걸린다.
    - 글자는 연산자(`Tj`·`TJ`·`'`·`"`)가 실행되기 **전에** 실린 문자열 길이로 센다. pypdf는 글자를 모아 두었다가 위치가 바뀔 때에야 넘겨 주기 때문이다.
    - 한 쪽의 문자열 바이트는 10만까지(빽빽한 한국어 쪽이 약 1만). 글꼴의 글자 대응표(ToUnicode)는 코드 하나를 여러 글자로 바꿀 수 있지만 pypdf 6.x가 대응 하나를 512바이트(256글자)로 제한하므로, 한 쪽에서 모아 둘 수 있는 글자는 최대 10만 × 256으로 묶인다.
- 내용 스트림 하나를 해석하는 동안(연산자를 넘겨 주기 전)은 pypdf 자체 상한(해석량 200만)에 맡긴다. 위의 최악값(한 쪽 2,560만 글자)은 상한으로 묶이지만 작지 않다. 그래서 **글자 뽑기를 별도 프로세스에서 한다**(아래, #52).
- 남은 위험 (이름 인식 모델, D23, 게이트웨이 안에서 돈다): 글자 상한(200만 자)까지 채운 파일은 이름 인식 모델이 읽는 데 **1분 안팎** 걸린다(256토큰 구간을 8개씩 묶어 계산, 11/07 이 PC 측정: 7.6만 자 2.5초). 시간은 글자 수에 비례하고 상한으로 묶인다. 보통 문서(수만 자)는 몇 초 안이다. 큰 파일을 반복해 올리면 그동안 CPU를 쓴다. 이 PC 안에서만 요청을 받는 기본 설정(D20)에서는 이대로 두고, 외부에 열 때 파일 크기 상한을 낮추거나 별도 작업으로 돌린다.

## 별도 프로세스 (#52, 11/23)

파일 검사와 채팅이 같은 프로세스면 악성 파일 하나가 라이브러리 안에서 시간·메모리를 많이 써 게이트웨이 전체를 느리게 하거나 멈출 수 있다(유출이 아니라 가용성 문제). 그래서 파일마다 작업 프로세스(`gateway/files/worker.py`)를 띄워 글자만 뽑는다(`gateway/files/isolate.py`).

- **메모리 1GB**: 작업 프로세스가 시작하자마자 자기에게 상한을 건다. Windows는 Job Object(`JOB_OBJECT_LIMIT_PROCESS_MEMORY`), 그 밖은 `setrlimit(RLIMIT_AS)`. 넘으면 할당이 실패해 "메모리를 너무 많이 써서 멈췄습니다"(`too_long`). 상한을 걸지 못하면 읽지 않는다(`isolation_failed`)
- **시간 60초**: 넘으면 게이트웨이가 작업 프로세스를 강제로 끄고 `too_long`. PDF 자체 상한(30초)보다 길게 잡아 보통은 그쪽이 먼저 이유를 알려 준다
- **동시 2개**: 최악이어도 메모리는 2GB로 묶인다. 넘치면 차례를 기다린다. 값은 운영자가 골랐다(11/23)
- 형식·크기는 파일을 열지 않고 게이트웨이에서 먼저 본다(지원하지 않는 형식에 프로세스를 띄우지 않는다). 작업 프로세스는 글자만 돌려주고 가명화(이름 인식 모델)는 게이트웨이가 한다(파일마다 모델을 다시 올리지 않게)
- 작업 프로세스의 오류 출력은 쓰지 않는다(라이브러리 오류에 파일 내용 일부가 섞일 수 있다). 창 없이 띄운다(Windows `CREATE_NO_WINDOW`, `start.ps1`로 창 없이 켠 게이트웨이와 같이)
- 확인(`tests/test_file_isolation.py`): 같은 파일을 안·밖에서 뽑은 결과가 같다. 멈추는 작업 프로세스는 시간 상한에서 꺼지고, 4GB를 잡으려는 작업 프로세스는 메모리 상한에서 멈춘다. **작업 프로세스가 멈춰 있는 동안에도 실제 포트의 게이트웨이가 채팅·상태 확인에 2초 안에 답한다**
- 추가 지연(11/23 이 PC, `bench/run_file_isolation.py`, 5번 중앙값): 파일 한 번에 **0.09~0.36초**. 새 파이썬 프로세스와 그 형식의 라이브러리를 불러오는 시간이다(엑셀이 가장 길다). 예상(0.5~1초)보다 작아 프로세스를 미리 띄워 두지 않는다

| 파일 | 크기 | 프로세스 안 | 별도 프로세스 | 추가 |
|---|---|---|---|---|
| docx | 37KB | 24ms | 192ms | +168ms |
| xlsx | 5KB | 2ms | 366ms | +364ms |
| pdf | 1KB | 1ms | 175ms | +175ms |
| csv | 1KB 미만 | 0ms | 86ms | +86ms |
| csv (2.5만 줄) | 1,318KB | 10ms | 122ms | +112ms |
