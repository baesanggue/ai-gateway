## 진행 중 결정

### D10. 판단 정확도 대응을 앞당기고, 시간 제한을 완화한다 (2026-10-26, #18)

- **배경**: #5 간이 테스트에서 기본 `laya:multilingual`은 기준값 0.5에서 한국어 판단에 쓸 수 없었다. 민감정보·원본 필요는 AUC 0.8 이상으로 신호가 있었지만, 라우팅의 핵심인 난이도·의도는 신호가 없었다. 원래 계획은 "11/11 벤치마크로 파인튜닝 여부를 정하고, 11/17 전에는 하지 않는다"였다.
- **결정**
  1. 대응 순서를 정한다: ① 기성 판단 모델 교체(설정 한 줄) → ② 질문별 기준값·temperature 보정 → ③ 한국어 파인튜닝. 앞 단계가 목표를 넘으면 뒤 단계는 하지 않는다.
  2. 판단 시점을 11/11에서 **10/28**로 앞당긴다. ③이 필요하면 10/29부터 M1과 병행해 11/9까지 마친다.
  3. 하루 2시간(주말 3시간)은 상한이 아닌 기준으로 바꾼다. 11/17에 완성된 시연을 하는 것이 우선이다.
- **이유**: "11/17 전 파인튜닝 금지"는 하루 2시간 예산 안에서 필수 기능을 먼저 지키고, 근거 없이 시간을 쓰지 않으려는 위험 관리 규칙이었다. 근거가 2주 먼저 나왔고 시간 예산도 풀렸으므로, 날짜를 지키느라 대응을 미루면 오히려 미완성으로 발표할 위험이 커진다.
- **포기한 것**: 엄격한 시간 예산. 대신 하루 이슈 1~2개 단위와 매일 커밋은 유지한다.
- **모델 비교의 잠정 기준 ("가벼움")**: CPU에서 질문 5개 2초 이내, 메모리 4GB 이하. 무거운 로컬 LLM을 넣지 않는다는 원칙 P3의 취지를 숫자로 정의한 것이다. (사용자 확정 대기)

### D11. 판단 모델은 바로 바꾸지 않고, 같은 시험지로 재서 고른다 (2026-10-26, #18)

- **배경**: 20문장 비교에서 `d1:3b`만 보정 없이 한국어 판단이 됐다(민감정보 8/8·오탐 0, 난이도 0.92). 하지만 CPU에서 질문 11개에 10초가 걸리고, 라이선스(LFM Open License)에 연 매출 1,000만 달러 이상 기업의 상업 사용 제한이 있다. `laya:multilingual`은 Apache-2.0이고 CPU에서 질문당 0.07초로 빠르지만, 기본 상태의 정확도가 부족하다. Laya 공식 README에 따르면 파인튜닝 효과가 크고(0.36 → 0.766), `laya-serve`가 `/v1/systemone`을 제공한다.
- **결정**
  1. 10/28: 라벨을 검토한 100문장으로 `d1:3b`와 `laya:multilingual`의 기본 상태를 비교해 **목표선**을 정한다.
  2. 10/29~11/4 (M1과 병행): Laya 한국어 파인튜닝 시범. **서빙 경로(`laya-serve`로 우리 가중치를 불러와 `/v1/systemone`으로 답하는지)를 가장 먼저 확인하고, 안 되면 중단한다.**
  3. 11/5까지 같은 100문장 점수로 최종 모델을 정한다. 그 전까지 `config.yaml`은 `laya:multilingual`로 둔다.
- **학습 데이터**: 학교에서 지원받은 LLM API로 만든다. 라벨은 생성 조건으로 정한다(예: "주민번호 실제 값이 필요한 요청을 만들어라" → `needs_raw_value=1`). 다른 판단 모델의 출력을 정답으로 쓰지 않는다. 테스트셋 문장·이름과 겹치지 않게 한다.
- **이유**: 두 후보의 강점이 정반대다(정확도 vs 속도·라이선스). 그래서 어느 쪽을 믿을지 고민하지 않고 같은 시험지로 재서 숫자로 고른다.

### D12. 원본을 봐야 하는 판단은 로컬, 가명화 문장으로 충분한 판단은 클라우드 (2026-10-27, #25)

- **배경**
  - 면담 의견: 가벼움이 차별점이면 성능이 받쳐 주는 데까지로 활용 범위를 줄이라.
  - 100문장 비교: 라이선스 제약 없는 소형 로컬 모델(`gliclass:v4-edge`)은 민감정보·기밀 판단이 좋았다. 클라우드 판단 API(OpenAI Decisions)는 가명화된 문장만으로 라우팅·위험·원본 필요를 잘 판단했다. (`docs/model-evaluation.md`)
- **결정**
  1. 판단을 "원본을 봐야 하는가"로 나눈다.
     - **로컬** (`gliclass:v4-edge`, Apache-2.0, CPU): 정규식이 놓친 이름·주소가 남았는가, 기밀인가
     - **클라우드** (OpenAI Decisions, 가명화된 문장): 원본 값 필요(가명화된 개인정보가 있을 때만 묻는 코드 조건), 위험·인젝션, 난이도, 의도
  2. 순서: 가명화(코드) → FAQ 확인(코드) → 로컬 판단(차단이면 여기서 끝) → 클라우드 판단 → LLM. 클라우드에는 가명화된 문장만 간다.
  3. 클라우드가 판단을 거부(refusal)하면 차단 쪽으로 처리한다. 클라우드가 응답하지 않으면 저렴한 모델로 보내는 대체 경로를 둔다.
     - **(10/30 변경, D16)** 위험·원본 필요 질문의 거부만 차단한다. 난이도·의도 질문의 거부는 고성능 모델로 보낸다.
  4. 사양별 프로필은 두지 않는다. 일반 사무용 PC의 CPU로 동작한다.
  5. 판단까지 전부 로컬인 구성(파인튜닝한 Laya)은 M6의 "완전 로컬" 옵션으로 미룬다(#20~#22).
- **이유**
  - 보안 약속의 기준은 "어디서 계산하느냐"가 아니라 "원본이 어디로 가느냐"다.
  - LLM에 어차피 가명화된 문장을 보내므로, 같은 문장을 클라우드 판단에 보내도 새로 나가는 정보가 없다. 예외는 FAQ인데, FAQ는 코드가 먼저 걸러 밖으로 내보내지 않는다.
  - 로컬 모델의 역할이 줄어 0.4B급 모델과 CPU로 충분하다(메모리 실측 2.2GB, 질문 2개 약 0.35초).
  - 클라우드 판단 비용은 요청당 약 $0.00008로, 라우팅으로 아끼는 비용에 비해 무시할 수준이다.
- **포기한 것**: "판단도 전부 로컬"이라는 표현과 인터넷 없이 동작하는 라우팅. 단, LLM 호출에는 어차피 인터넷이 필요하다.
- **바뀐 원칙**: 강점 1번은 "판단도 로컬에서 한다" → "원본을 봐야 하는 판단은 로컬에서 하고, 밖으로는 가명화된 문장만 나간다". 설계 결정 1·5번의 "Laya"는 "판단 모델"로 바꾼다. README와 구조도는 M4에 갱신한다.

### D13. 범용 구조로 만들고, 여러 업종으로 검증한다 (2026-10-28, #27)

- **배경**: 제품 정의(타깃: AI 기능을 운영하는 중소기업 개발팀·보안 담당자)는 처음부터 범용이었다. 그런데 테스트셋(CLAUDE.md §5)과 시연(§7)이 쇼핑몰 기준이었고, 판단 질문의 의도 선택지도 "배송·반품·결제"로 업종에 묶여 있었다.
- **결정**
  1. **업종과 무관한 핵심**(가명화·복원, 보안 판단, 라우팅 정책, OpenAI 호환 엔드포인트)과 **업종별 설정**(FAQ 목록·템플릿 답변, 사용자 사전)을 나눈다. 업종별 설정은 회사가 `config.yaml`에 등록한다.
  2. 의도 선택지를 업종과 무관하게 바꾼다: FAQ(회사가 정해 둔 답이 있는 질문) / 상품·서비스 이용 문의 / 업무 처리 / 무관. 이용 문의와 업무 처리는 라우팅상 같은 경로라 평가에서는 묶는다.
  3. 테스트셋에 **의료(M)·금융(F)·공공민원(G)** 각 30행을 같은 범주 비율로 추가한다(총 190행). 결과는 업종별로 나눠 보고한다.
  4. 30초 시연은 쇼핑몰 하나로 한다. 범용성은 "설정만 바꾸면 다른 회사" 장면으로 보여 준다.
- **라벨 원칙 (10/28)**: 난이도가 애매하면 고성능으로 둔다. 라우팅 정책의 "신뢰도가 낮으면 고성능"과 같은 원칙이다. 가명화는 "같은 값 = 같은 토큰" 규칙을 지킨다(M2 완료 기준).
- **이유**: "범용"은 주장이 아니라 근거가 필요하다. 한 업종 데이터로 잰 점수로는 다른 업종에서도 된다고 말할 수 없다.
- **포기한 것**: 업종마다 30행이라 업종별 수치는 흔들림이 크다(기밀·위험은 업종당 2행). 업종별 결과는 경향을 보는 용도로 쓰고, 기준값은 전체 190행으로 정한다.

### D14. M0 검증 결과와 정확도 목표 (2026-10-28, #6)

- **M0 검증 결과**: 채택 구성(D12: 로컬 `gliclass:v4-edge` + 클라우드 Decisions)이 190행·업종 4개에서 동작함을 확인했다 (`bench/results/compare-190-2026-10-28/summary.md`).
- **정확도 목표**: 파인튜닝 여부를 가르던 기준을, M2(가명화된 문장으로 재측정)·M3(발표용 벤치마크)에서 성능이 떨어지지 않았는지 보는 **경보선**으로 쓴다.

| 판단 | 목표 | M0 결과 (190행) |
|---|---|---|
| 민감정보 (로컬) | 재현율 ≥ 95% | 98% (56/57) |
| 원본 필요 (클라우드) | 재현율 ≥ 85%, 오탐 ≤ 2% | 89%, 0.6% |
| 위험·인젝션 (클라우드) | 재현율 ≥ 95%, 오탐 ≤ 1% | 100%, 0% |
| 기밀 (로컬, 엄격 수준, 기준값 0.12) | 재현율 ≥ 90% | 92%, 오탐 11% |
| 난이도 | 정확도 ≥ 85% | 94% |
| 의도 | 정확도 ≥ 90% | 96% (판단 거부 제외) |
| 판단 거부로 막히는 정상 요청 | ≤ 1% | 2.7% (4/147) → **0% (D16, 10/30)** |

- (10/30 정정) 판단 거부 행의 M0 결과를 처음에 2.4%로 적었는데, 분모를 거부되지 않은 문장 수(164)로 잡은 잘못이었다. 차단 대상이 아닌 문장 수(147)로 나누면 2.7%다.
- **이유**: 목표를 현재 수치보다 약간 낮게 잡는다. M2에서는 측정 조건(가명화된 문장)이 바뀌고, 190행이라 몇 행 차이로 수치가 흔들린다. 아직 못 넘은 목표(판단 거부)를 하나 넣어 다음 작업의 방향을 정한다.

### D15. 파인튜닝은 비교군·포트폴리오용으로, 개발을 우선하며 병행한다 (2026-10-28, #20~#22)

- **목적**: 현재 구성(로컬 gliclass + 클라우드 Decisions)과 **파인튜닝한 Laya 하나로 6개 판단을 전부 로컬에서 하는 구성**을 같은 190행으로 비교한다. 이기면 "완전 로컬" 옵션이 되고, 지면 하이브리드를 택한 근거가 된다. 어느 쪽이든 포트폴리오 결과물이다.
- **진행 규칙**
  1. 그날의 개발 이슈를 먼저 끝낸다. 파인튜닝은 남는 시간에만 한다.
  2. GPU가 혼자 돌 수 있는 작업(데이터 생성, 학습) 위주로 걸어 두고 개발을 계속한다.
  3. 마일스톤이 밀리면 즉시 멈추고 M6로 미룬다.
  4. 순서: #20 서빙 경로 확인(안 되면 중단) → #21 학습 데이터 생성 → #22 학습·평가.
- **확인한 사실 (Laya 공식 저장소)**
  - 학습 함수: `laya.train.finetune(data, model_dir, output_dir, config, device)`. temperature 보정을 함께 한다.
  - 공개된 스크립트는 MPS·CPU용이라, 이 PC의 RTX 4080(CUDA)용 짧은 스크립트를 `finetune/`에 만든다.
  - 학습 데이터 형식은 JSONL 한 줄에 `{"state", "questions", "gold"}`이다. `gold`는 질문마다 `label`과 `probabilities`(확률 분포)로 적는다.
  - 서빙: `laya-serve`가 `/v1/systemone`을 제공한다. 우리가 학습한 가중치를 불러올 수 있는지는 #20에서 확인한다.
- **(10/29) #20 통과**: `laya-serve`가 `LAYA_EXTRA_MODELS`로 등록한 로컬 체크포인트를 `/v1/systemone`으로 서빙함을 확인했다 (`docs/laya-serve-notes.md`). 트랙을 계속한다.
- **학습 데이터 출처**: 학교 키가 일반용이라 OpenAI·xAI 출력은 쓰지 않는다(`docs/llm-api-notes.md` §3). 출력 사용 제한이 없는 로컬 오픈 모델(라이선스는 시작할 때 확인), 코드 템플릿, AI Hub 판결서 익명처리(로컬에서만 사용)를 쓴다. 테스트셋은 절대 학습에 넣지 않는다.

### D16. 판단 거부: 라우팅 질문의 거부는 고성능으로, 다시 묻지 않는다 (2026-10-30, #8)

- **배경**
  - D12에서 정한 "판단 거부 → 차단" 방식은 정상 요청 4건(4/147 = 2.7%)을 막았다. D14 목표(≤ 1%)를 넘는다.
  - 190행에서 거부는 전부 난이도·의도 질문에서 나왔다. 위험·원본 필요 질문은 26문장 모두에서 정상으로 답했다.
  - 거부된 질문만 따로 다시 물어도 26문장 모두 똑같이 거부했다. 10/28, 10/30 두 번 측정했고 세 번 모두 같았다. 다른 질문과 같이 물어서 생긴 거부가 아니라 문장 내용 때문에 매번 같은 결과가 나오는 거부다. (`bench/results/refusal-retry-2026-10-30/`)
  - 거부된 26문장 중 차단 대상 22문장은 위험·원본 필요 판단으로 **이미 전부 차단된다**. 거부 규칙만 잡아내는 차단 대상은 없었다.
  - 막히던 4문장: 기밀이 담긴 정상 업무 요청 2건(T082, M025), `[주민번호1]` 토큰이 든 안내문 1건(G019), 측정용 가명화 근사가 계좌번호를 잘못 가린 문장 1건(F018)
- **결정**
  1. 위험·원본 필요 질문의 거부 → 차단 (`decision.cloud.on_refusal: block`, 그대로)
  2. 난이도·의도 질문의 거부 → 고성능 모델 (`decision.cloud.on_routing_refusal: premium`). "애매하면 고성능" 방침과 같다.
  3. 거부된 질문을 다시 묻지 않는다. 효과 없이 지연과 토큰만 늘어난다.
- **결과**: 판단 거부로 막히는 정상 요청 2.7% → **0%**. 차단 대상 22문장은 그대로 차단된다.
- **남은 위험**: 위험 판단이 놓치고 난이도·의도만 거부되는 위험 요청이 있으면, 그 요청은 고성능 모델로 간다. 테스트셋에서는 없었다. 고성능 모델 자체의 안전 장치가 한 번 더 거른다. M3 벤치마크에서 다시 확인한다.

### D17. LLM: 저렴한 모델 `gpt-6-luna`, 고성능 모델 `gpt-6.1-sol` (2026-10-30, #9)

- **후보**: 학교 키로 접근 가능한 채팅 모델 77개 중 지원 종료가 정해지지 않은 GPT-6 계열. 가격은 공식 가격 페이지에서 확인했다 (`docs/llm-api-notes.md` §1).
- **실제 호출** (시연 4번 사과 메일, 가명화된 문장, 1회씩): `gpt-6-luna`(none) 2.9초·$0.00006, `gpt-6.1-terra`(none) 2.6초·$0.00055, `gpt-6.1-sol`(low) 5.2초·$0.0022, `gpt-6-sol`(none) 2.9초·$0.0013. 모두 Chat Completions로 호출되고 한국어 품질이 자연스러웠다.
- **결정**
  - 저렴한 모델: `gpt-6-luna`, 추론 강도 `none`. 현재 세대에서 가장 싸고, 클라우드 판단(Decisions)과 같은 모델 계열이다.
  - 고성능 모델: `gpt-6.1-sol`, 추론 강도 `low`(가장 낮은 값). 구형 `gpt-6-sol`과 가격이 같고 더 최신이다.
- **이유**
  - 요청 1건 비용이 약 37배 차이라 라우팅의 절감 효과가 분명하다.
  - 최상위 `gpt-6-astra`를 비교 기준으로 쓰면 절감률이 실제보다 부풀려 보인다. "실제로 쓸 만한 고성능 모델"을 기준으로 삼는다.
  - `gpt-5-nano`·`gpt-5-mini`는 12/11 지원 종료라 최종 평가(12/8) 직후 시연이 깨질 수 있다.
- **함께 발견한 문제**: 일부 모델이 `[고객1]`을 "고객님"으로 바꿔 써서, 복원할 토큰이 답변에서 사라졌다 → #9에서 시스템 지시로 시험한다.
