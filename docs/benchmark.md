## 최근 결과: 동시 접속 (11/13, `bench/results/load-2026-11-13/summary.md`, #115)

발표 날 반 전체가 QR을 보고 한꺼번에 보내는 경우를 쟀다(`bench/run_load.py`).
- 보낸 길: 체험판 화면과 같은 `/v1/chat/completions`
- 보낸 방식: 한 단계의 요청을 같은 순간에 출발시켰다
- 문장: '해 볼 것' 4가지를 섞고, 가린 뒤에도 겹치지 않게 해서 판단 캐시를 쓰지 않았다
- 실행 PC: Ryzen 7 7800X3D, 판단은 CPU

| 동시 요청 | 성공 | 화면이 받은 시간 (평균 / 최대) | 로컬 판단 (평균 / 최대) | 클라우드 판단 (평균 / 최대) |
|---|---|---|---|---|
| 1 (차례로 4개) | 4/4 | 1.7 / 3.2초 | 0.21 / 0.22초 | 0.26 / 0.27초 |
| 10 | 10/10 | 2.3 / 4.5초 | 0.79 / 1.35초 | 0.30 / 0.38초 |
| 20 | 20/20 | 3.5 / 6.3초 | 1.50 / 2.83초 | 0.27 / 0.41초 |
| 30 | 30/30 | 4.4 / 8.0초 | 2.20 / 4.20초 | 0.28 / 0.62초 |

- **69건 모두 성공했다.** 화면 제한(120초)을 넘은 요청은 없다. LLM 비용은 $0.01이다.
- **몰리는 곳은 로컬 판단이다.** Ollaya가 판단을 한 번에 하나씩 처리해서 기다리는 시간이 약 0.19초 간격으로 계단처럼 늘어난다(30개일 때 0.2초부터 4.2초까지 22개). 클라우드 판단은 동시 요청 수와 관계없이 일정했다.
- **한계(추정)**: 판단이 필요한 요청이 같은 순간 약 50개를 넘으면 마지막 요청의 로컬 판단이 제한 시간(10초, `decision.timeout_seconds`)에 닿는다.
  - 기본 수준(체험판): 기밀 판단을 건너뛰고 가명화해서 진행한다
  - 엄격 수준: 막는다(D19)
  - 실제 강의실에서는 사람마다 보내는 순간이 흩어지므로 이보다 여유가 있다
- **동시에 처리해도 개인정보가 새거나 섞이지 않았다.**
  - 요청 기록의 가린 문장에 남은 가상 값: 0개
  - 다른 요청의 값(요청마다 다른 전화번호·도로 번호)이 섞인 답: 0개 (LLM이 답한 32건)
- 30개 단계의 '가리기' 문장 8개 중 2개는 막혔다. 클라우드 판단이 "실제 값이 필요하다"고 봤다(신뢰도 0.64, 0.96).
  - 부하 탓이 아니다. 같은 문장을 한 번에 하나씩 다시 보내도 같은 신뢰도로 막혔고, 세 번 잰 것 모두 같은 두 문장이었다.
  - 시험용으로 바꾼 문장("배송이 49일 늦어진 것")에 대한 판단이다. 체험판 안내 문장은 그대로 통과한다.
- 같은 문장을 그대로 치면 판단 캐시를 써서 이보다 빠르다.
- 재는 법: 게이트웨이를 새로 켠 뒤 한 번만 잰다. 같은 게이트웨이로 다시 재면 첫 실행의 판단 결과가 캐시에 남아 로컬 판단을 재지 못한다(11/13 두 번째 실행에서 50건 모두 캐시). 요약에 캐시를 쓴 요청 수가 나온다.

## 최근 결과: 답변 품질 (11/12, `bench/results/quality-2026-11-12/summary.md`, #62)

질문: "이름·번호를 가려서 보내면 답이 나빠지지 않나요?" 게이트웨이가 실제로 가려서 보내는 요청 38개(개인정보 있음·원본 값 필요 없음·LLM 경로)로 쟀다. 원문을 그대로 보낸 답(A)과 가려서 보낸 뒤 복원한 답(B)을 같은 모델에서 받았다. 고성능 모델이 어느 쪽이 가린 것인지 모르게, 순서를 섞어 채점했다. 원문이 밖으로 나가는 유일한 측정이라 테스트셋의 가상 값만 썼다. 비용 $0.33, 13분.

| 기준 (1~5) | 원문 | 가명화 → 복원 | 차이 |
|---|---|---|---|
| 요청 충족 | 4.76 | 4.79 | +0.03 |
| 정확성 | 4.61 | 4.55 | −0.05 |
| 자연스러움 | 4.97 | 4.68 | **−0.29** |

- **어느 쪽이 나은가**: 같다 17 · 원문 13 · 가린 쪽 8. 같거나 가린 쪽이 나은 비율은 66%(25/38)다.
- **대조군**: 원문 답을 한 번 더 받아 원문끼리 비교했다. 아무것도 가리지 않아도 채점자는 39%에서 한쪽을 골랐다. 한쪽에 20%쯤씩이다. 가명화 비교에서 원문 쪽은 34%였다. 그러니 가명화 때문에 원문이 나았던 것은 15%p쯤이다.
- **원문이 나았던 13건의 원인**

  | 원인 | 건수 | 처리 |
  |---|---|---|
  | 호칭이 딱딱함("[고객1]께", 이름만 부름) | 5 | 지시문 보완 |
  | 그 사람의 번호·이메일 토큰을 회사 문의처·보내는 사람으로 씀 | 3 | 지시문 보완 |
  | 이름 인식 모델이 조사까지 주소로 봐 "7로로"로 복원 | 1 | 가명화 수정 |
  | 답에 "자리표시자"라는 말 | 1 | 지시문 보완 |
  | 요청에 없던 토큰 `[고객1]`을 지어냄 → 사용자에게 그대로 보임 | 1 | 한계로 기록 (`docs/limitations.md` §4) |
  | 가명화와 무관한 답의 차이(받는 사람 줄 생략, 발송 방식 단정) | 2 | — |

- **고친 것 (11/12)**
  - 가명화: 번호·호·층·번지 뒤의 조사는 주소 값에서 뺀다. 가명화 측정은 11/11과 같다.
  - 토큰 지시문(`config.yaml llm.placeholder_instruction`): 호칭은 토큰 뒤에 붙인다("[고객1] 고객님"). 그 사람의 연락처 토큰을 문의처로 쓰지 않는다. "자리표시자"라는 말을 쓰지 않는다.
- **고친 뒤 확인은 테스트셋 밖 문장으로 했다.** 같은 38건으로 다시 재면 테스트셋에 맞춘 개선이 된다. 그래서 발표 수치는 고치기 전 값이다. 확인에는 저렴한 모델을 썼다.

  | 문장 | 옛 지시문 | 새 지시문 |
  |---|---|---|
  | 시연 4번("김민수 고객(010-1234-5678)에게 배송 지연 사과 메일 써줘"): 문의처 오용 | 6/35 (17%, 세 번 돌림: 2/5·0/10·4/20) | **0/20** |
  | 새 문장 8개 × 2 (쇼핑몰·의료·금융·공공, 가상 값): 문의처 오용 | 1/16 + 모호한 문장 2 | **0/16** |
  | 이름 토큰 유지 | 36/36 | 36/36 |
  - 새 문장 하나("…안내 메일 써 줘, 연락처는 010-5555-6666")는 그 번호를 메일에 넣으라는 뜻으로도 읽혀서 오용으로 세지 않았다.
  - 고성능 모델은 몇 문장만 눈으로 확인했다. "김민수께," → "김민수 고객님,", "오세린," → "오세린 님,".
- 사람이 직접 볼 10쌍은 `review.md`에 있다(원문이 나았던 것부터).

## 최근 결과: 게이트웨이 전체 (11/08, `bench/results/gateway-2026-11-08/summary.md`)

실행 PC: AMD Ryzen 7 7800X3D, 32GB, Windows 11. 판단·이름 인식은 CPU에서 돌린다. 실제로 쓴 비용은 $0.77이다.

| 지표 | 값 |
|---|---|
| 경로 정확도 (기본 수준) | **89%** (169/190). FAQ를 등록하지 않은 업종(금융·공공)의 템플릿 10행을 빼면 94%, 쇼핑몰(시연 업종) 97% |
| 경로 정확도 (엄격 수준) | 84%. 기밀 판단 오탐으로 정상 요청 14개가 막힌다 (#46에서 본 오탐 12%와 같은 원인) |
| 라벨 기준 | 집계할 때의 testset. 11/08 T075를 원본 필요로 고쳤다(#67, 번호 비교는 원본 필요). 측정은 다시 하지 않았다 |
| 단순 요청 비용 | 템플릿 100%, 저렴한 모델 95% 절감 |
| 전체 비용 절감 | **10%** (이 테스트셋은 고성능 경로가 46%다). 복잡한 요청이 10%면 48%, 20%면 30% (측정한 경로별 평균으로 계산한 가정) |
| 판단 지연 | 평균 502ms, p95 650ms (로컬 + 클라우드) |
| 전체 지연 (LLM 포함) | 평균 7.6초, p95 36초 (고성능 모델의 긴 답이 대부분) |
| 밖으로 나간 원본 값 | **1문장**: T056 "정하늘" (이름 인식 모델이 놓친 이름, #58. 이름을 사전에 등록하면 0) |
| 복원하지 못한 토큰 | 1개 (T053: LLM이 요청에 없는 `[고객1]`을 만들어 씀) |

### 읽는 법
- **비용 절감은 요청 구성에 달렸다.** 고성능 경로 요청 하나가 평균 1,140토큰을 출력해 약 $0.0115가 든다. 단순 요청은 고성능 가격으로 쳐도 $0.001 안팎이다. 그래서 복잡한 요청이 많을수록 전체 절감률이 낮다.
- "전부 고성능" 비용은 D18대로 보수적으로 잡았다. 차단된 요청은 넣지 않았고, 고성능 모델이 더 길게 쓰는 경향(1.48배)도 넣지 않았다.
- 기대와 다른 경로의 원인 (기본 수준 11행)
  - 판단 거부 → 고성능 (D16): 4행. 주민번호·전화번호 토큰이 든 요청에서 난이도·의도 판단을 거부했다.
  - 업종을 모르는 의도 판단: 은행에 온 "적금이랑 예금 차이"를 무관으로 막았다. 반대로 은행에 온 "다이어트 식단 짜 줘"는 업무로 봤다.
  - 이름 인식 모델의 오탐: "건강검진 전날 금식은…"에서 "금식"을 `[이름1]`로 가렸다. 그 뒤 문장이 "원본 필요"로 판단되어 막혔다.
  - (해결) 두 전화번호가 같은지 묻는 요청(T075): 판단은 "원본 필요", 라벨은 저렴한 모델이었다. 11/07에 정한 원칙(번호 비교는 원본 필요)에 맞춰 라벨을 고쳤다(#67).

## 최근 결과: 신뢰도 보정 (11/08, `bench/results/calibration-2026-11-08/summary.md`)

| 판단 | 신뢰도 0.8 미만 | 0.8 이상 |
|---|---|---|
| 위험 (클라우드) | 100% | 100% |
| 난이도 (클라우드) | 96% | 100% |
| 의도 (클라우드) | 87% | 99% |
| 원본 필요 (클라우드) | 100% | 96% |
| 기밀 (로컬) | **36%** | 99% |

- `min_confidence`는 두지 않는다(D24). 값을 올려도 경로 정확도가 오르지 않았다.
- 로컬 기밀의 신뢰도가 낮은 구간에서 맞지 않는 것은 공식 탓이다. 신뢰도는 0.5에서 떨어진 거리를 재는데 기준값이 0.10이다. 그래서 화면에는 확률과 기준값을 보여 준다(D24).
